# ローカル統合安定化仕様

## 目的

recwatch の主要な管理画面を rectime-api の実際の契約に接続し、固定データや未実装の操作を本番相当の画面から排除する。既存のUI方向性は維持し、既存コンポーネントとデザイントークンを再利用する。

この作業はローカル専用ブランチで行い、明示的な依頼があるまで push、Pull Request、merge、Issue更新は行わない。

## 設計方針

- APIの外部データは各機能の境界で検証・正規化し、画面から生のレスポンス形状を参照しない。
- バックエンドの現在のHTTP契約を基本の正本とし、契約自体に欠陥がある場合だけ後方互換な修正を加える。
- 画面固有の通信、変換、状態管理、表示を分離し、1ファイルに複数の責務を集めない。
- 新しい抽象化や依存ライブラリは、複数箇所の重複を実際に解消するときだけ追加する。
- UIは既存の共通コンポーネントとセマンティックトークンを優先し、色・角丸・影の直書きを増やさない。

## 監査で確認済みの不具合

1. CSV / Excel取り込み
   - フロントは作成結果の `import_id` を参照している。
   - APIは `validated_file_id` を返すため、成功後に `/master-imports/undefined` が呼ばれる。
2. 通知作成
   - リクエスト形状は概ね一致しているが、APIが `EVENT_DATE` と送信日時の一致を要求する。
   - ローカル設定と画面の現在日時が異なると作成できず、内部失敗時には500となる。
3. 認証・プロフィール画像
   - `/api/v1/auth/me/photo` の404が画面遷移ごとに繰り返される。
   - 401後の更新は成功するが、不要な再試行と重複取得が多い。
4. ダッシュボード
   - 実在する `/events` ではなく未登録の `/sports` へリンクしている。
   - 色、角丸、影が画面ファイルに直書きされている。
5. 参加者管理
   - 表示データが固定値で、実APIと接続されていない。
6. 未提供機能
   - 大会、採点、計測、レポート、チームなどにプレースホルダー画面がある。
   - バックエンド契約がない機能を動作する機能のようにナビゲーションへ表示している。
7. 検証の不足
   - フロント162件、バックエンド747件のテストと両ビルドは成功するが、上記の実通信不具合を検出できていない。

## 実装順序

### Slice 1: 境界の重大不具合

- 取り込み作成レスポンスを境界DTOから内部モデルへ正規化する。
- `undefined` のIDでは遷移・通信できない検証を追加する。
- ダッシュボードのリンクを登録済みルートへ修正する。
- 失敗を先に再現する単体・統合テストを追加する。

### Slice 2: 認証と共通通信

- 画像が存在しない結果をセッション中に記録し、404の連発を止める。
- 認証更新後の再送とエラー表示を統一する。
- 同一画面で発生する不要な重複取得を減らす。

### Slice 3: 通知

- イベント開催日を画面が取得できる契約にし、作成可能日時を一致させる。
- 400 / 404 / 409 / 500を利用者向けの意味あるエラーへ変換する。
- 作成、一覧、編集、削除をローカルAPIで往復確認する。

### Slice 4: 主要管理画面

- 学生、クラス、教官、競技、スケジュール、集合場所の取得・登録・更新後の再表示を確認する。
- ページング、空表示、読込中、通信失敗の状態を共通化する。
- `schedule/new` を含め、各ページに一意で意味のある見出しを置く。

### Slice 5: 参加者管理

- 固定データを撤去し、競技、集合、学生、集合メンバーAPIから表示モデルを構築する。
- 登録・解除後に再読込なしで画面へ反映する。
- 重複や時間競合の判定は、APIに正本ルールがある場合のみ実装する。

### Slice 6: UI整理

- 到達可能な画面の直書きUIを既存部品へ段階的に置き換える。
- 同じ責務の重複部品を、利用箇所を確認した上で統合する。
- 未提供機能は、要件とAPIが決まるまで本番相当ナビゲーションから隠す。

## 完了条件

- ローカル環境の主要導線で、予期しない400、401、404、409、500が発生しない。
- 到達可能な管理画面に固定の業務データと「未実装」操作が残らない。
- 取得・登録・更新・削除の各操作が、API結果と画面表示で一致する。
- APIレスポンスの形が変わった場合、境界テストが失敗する。
- フロント・バックエンドの型チェック、テスト、ビルドがすべて成功する。
- ブラウザでデスクトップ幅とモバイル幅の主要導線を確認し、コンソールエラーがない。
- GitHub上のブランチ、Pull Request、Issueには変更がない。

## 今回の範囲外

- 要件が存在しない大会方式、採点、計測、レポート計算ロジックを推測で新設すること。
- 大規模なフレームワーク変更、全面的なディレクトリ再編、不要な共通基盤の新設。
- 明示的な承認なしでのデータベース破壊的変更。
